CryptoPulse pre-work briefing

Stage 6: RSS-Enriched Sentiment Analysis

A beginner-friendly plan for giving the classifier more context than a headline, without introducing full-article scraping.

Prepared 16 September 2026 | Estimated reading time: 7 minutes

1. Today's objective

Objective: extend CryptoPulse so each news item can carry a cleaned RSS summary, then classify the headline and summary together while preserving headline-only behavior when no useful summary is available.

This stage improves the information supplied to OpenAI. It does not attempt to download complete articles, bypass paywalls, or scrape arbitrary websites. The scope stays deliberately small and reliable.

2. Where we are in the project

CryptoPulse already has an end-to-end production-style pipeline:

  1. Binance provides hourly market candles.
  2. Google News RSS provides recent cryptocurrency headlines, with GDELT as fallback.
  3. SQLite stores the normalized article and market records.
  4. OpenAI classifies unseen headlines for relevance, asset sentiment, and category.
  5. An exporter creates a safe public database snapshot.
  6. Streamlit presents the analytics.
  7. GitHub Actions repeats the refresh every six hours.

The current classification input is the headline. Stage 6 changes the article data contract and the classification input, while leaving the rest of this architecture intact.

3. What we are building and why

Current behavior

A short headline is normalized, checked for candidate assets, and sent to the model. This is fast and inexpensive, but context can be incomplete.

Stage 6 behavior

The headline remains primary evidence. A useful RSS description is cleaned, bounded, stored, and added as supporting context.

Headlines are often compressed or deliberately attention-grabbing. A summary may clarify who did what, which asset is actually affected, and whether the event is positive, negative, or merely descriptive.

Important limitation: RSS descriptions are not guaranteed to be useful. Some repeat the headline or contain publisher markup. Stage 6 must treat the summary as optional and fall back safely to headline-only classification.

4. Architecture and mental model

The new summary passes through the same layers as the headline: source parsing, validation, persistence, input preparation, classification, export, and display.

The key mental model is progressive enrichment. Every article must have a headline. Some articles additionally have a useful summary. Downstream code works in both cases.

5. Today's workflow

6. Explanation of each stage

1

Define the article contract

Add an optional summary to the canonical article model. Optional is essential because GDELT and some RSS items may not provide meaningful summary text.

2

Evolve the database safely

Add a nullable summary column to existing SQLite databases. Existing rows remain valid with NULL, so deployment data and local data can be opened without destructive rebuilding.

3

Extract and clean RSS descriptions

Read the RSS <description> field, decode HTML entities, remove markup, normalize whitespace, and reject descriptions that are empty or merely repeat the title. Cleaning belongs near ingestion because every downstream consumer should receive canonical text.

4

Build a bounded classification input

Prepare a clearly labelled input containing the headline and, when useful, the summary. Apply a character limit so one malformed feed item cannot create an unexpectedly large API request.

5

Version the classifier

Change the prompt version from the headline-only version to a new summary-aware version. The version is part of classification identity, so CryptoPulse can distinguish old outputs from new outputs instead of silently mixing two input methods.

6

Backfill deliberately

Recent articles already have headline-only classifications. A new prompt version makes them eligible for reclassification. Because the scheduled job is capped at 50 articles, the backfill should be controlled and its API cost understood.

7

Carry summaries into the safe snapshot

The exporter must include the nullable summary while continuing to exclude secrets, audit logs, and unnecessary working data. Streamlit may show the summary as supporting text, but headlines and links remain the primary interface.

8

Test and verify the complete path

Tests should cover useful summaries, duplicate summaries, HTML markup, missing descriptions, old-database migration, headline-only fallback, input limits, deduplication, safe export, and dashboard rendering. After deployment, verify one real scheduled run and the public app.

8. Important engineering concepts

Schema evolution

Changing a persistent data structure while preserving existing records and compatibility.

Backward compatibility

Old articles with no summary continue to behave correctly.

Progressive enrichment

Optional information improves a record without becoming a requirement for the pipeline.

Input normalization

External text is converted into a stable internal form before storage and modelling.

Model provenance

Prompt version, model, provider, and input text explain how each output was produced.

Bounded processing

Text length and article-count limits keep cost and runtime predictable.

9. Standard professional approach

A professional team usually handles this change in the following order:

  1. Write the new data contract and fallback behavior.
  2. Create a backward-compatible database migration.
  3. Normalize untrusted external content at the ingestion boundary.
  4. Keep model inputs explicit, structured, and size-limited.
  5. Version the changed model behavior.
  6. Plan reprocessing cost before launching a backfill.
  7. Test old and new records together.
  8. Deploy, observe one production cycle, and compare outcomes.

This order limits uncertainty. It ensures the storage layer understands the new field before the classifier or dashboard tries to use it.

10. What I should understand before coding

  • A summary is optional context, not a replacement for the headline.
  • External RSS content is untrusted input and must be cleaned before use.
  • Database migrations preserve data; they are different from deleting and recreating a database.
  • Changing classification input changes model behavior, so the prompt version must change.
  • Reclassification is a backfill and has a measurable API cost.
  • The existing Stage 3 metrics describe the headline-only system. We should not claim Stage 6 improves accuracy until it is evaluated.
  • The six-hour workflow and read-only Streamlit architecture remain unchanged in principle.
Recommended scope: implement summary storage and summary-aware classification first. Treat full-article extraction as a separate future stage because it introduces website-specific parsing, blocking, paywalls, and licensing concerns.

11. Expected state at the end of today's work

  • New Google News records store a cleaned summary when one is genuinely useful.
  • Existing and GDELT records without summaries still work.
  • OpenAI receives a labelled, bounded headline-plus-summary input.
  • A new prompt version keeps the outputs traceable.
  • The public snapshot safely carries summaries.
  • The dashboard can present supporting context without changing its core workflow.
  • Automated tests cover migration, parsing, fallback, classification, export, and UI behavior.
  • The scheduled refresh and public deployment complete successfully.

12. Short glossary

Backfill: processing existing records with a newly introduced rule, field, or model version.

Data contract: the agreed structure and meaning of data passed between components.

HTML entity: encoded text such as &amp; that must be decoded into its displayed character.

Nullable: a database field that may contain no value.

Normalization: converting varied external input into a consistent internal representation.

Prompt version: an identifier recording which instructions and input method produced a model result.

RSS: a structured XML feed used by publishers and aggregators to distribute article metadata.

Schema migration: a controlled change to the structure of an existing database.
